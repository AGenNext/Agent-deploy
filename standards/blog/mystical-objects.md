# Mystical Objects

*Every `import` is an act of faith.*

---

A Python library is a **mystical object.** You don't know what's inside. You didn't
write it. It changes under you with the next version. And somewhere, a dependency
you've never heard of can break — or quietly own — your whole system.

We have normalised **trusting code we cannot see, cannot verify, and do not
govern.** A whole industry, built on faith in black boxes.

## Why mystical objects are dangerous

- **Opaque** — you can't read what you depend on.
- **Mutable** — it changes every release; today's behaviour isn't tomorrow's.
- **Plural** — a thousand versions and forks; none canonical.
- **Ungoverned** — supply-chain risk: one compromised package, everywhere.

You **cannot verify a mystical object.** And what you cannot verify, you cannot
trust.

## The alternative: defined, not mystical

We hold to **data and contracts**, not mystical code. A contract is the *opposite*
of a mystical object: **defined, canonical, stable, governed, verifiable.** Code
still runs — but as a *conforming implementation* behind a contract you can read,
not a black box you pray to.

## For agents, it matters more

An agent that calls mystical objects **inherits their mystery** — it acts on
behaviour no one can verify. An agent that calls **contracts** acts on meaning
everyone agrees on. That is the difference between **Ultron and Jarvis** at the
library level.

> Stop importing mysteries. **Define the contract; let code conform. Only data is
> real.**
